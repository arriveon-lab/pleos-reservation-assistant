작성: 2026-11-07 KST. 기반: #2 장소 adapter. 후속 실행 이슈: [#12 REC-03](https://github.com/arriveon-lab/pleos-reservation-assistant/issues/12). 검토 대상: 장소 담당, #3 전화, #4 서버, #5 화면. 실제 데이터 사용 조건은 [#11](https://github.com/arriveon-lab/pleos-reservation-assistant/issues/11)에서 확인합니다. **팀 합의 전 제안이며 현재 OpenAPI·DB·제품 화면에 적용하지 않았습니다.** 사용 조건과 실제 adapter 검증은 [연동 검토](REC01_INTEGRATION.md), 현재 구현은 [STATUS](STATUS.md)를 따릅니다.

[REC-03 내부 세션 첫 구현](REC03_PREVIEW.md)에서 동시 합류·트랜잭션 거부·세대/취소·실행 상한을 가상 adapter로 검증했습니다. 이 구현은 아래 공개 API/화면 제안의 팀 합의를 대신하지 않으며 제품 endpoint도 추가하지 않았습니다.

## 먼저 결정할 사항

제안은 **외부 장소 검색 미리보기와 저장하는 예약 업무를 분리**하는 것입니다. 현재 `POST /searches`는 검색 후보와 최초 명령 응답을 H2에 저장하므로 Kakao 결과를 넣지 않습니다. 미리보기 분리 역시 세션 메모리 보유까지 허용됐다는 뜻은 아닙니다. [사업자 문의](https://devtalk.kakao.com/t/local-api/152647)의 답변을 확인하기 전에는 가상 응답으로만 개발합니다.

| 결정 | 제안 | 확인할 담당 / 채택 조건 |
| --- | --- | --- |
| 외부 미리보기 | 기존 저장 검색과 독립된 경계. 장소 데이터가 검색·명령 snapshot을 거치지 않음 | #2·#4: 일시 보유/표시 범위 확인 후 URI·요청·응답을 OpenAPI로 확정 |
| 예약 기능의 데이터 | 별도 허용을 받은 사업자 데이터 또는 직접 사용 권한을 확보한 매장 정보 | #2·#3·#4: 저장·재사용·전화 공급자 전달 근거 확인 |
| 실제 장소 + 모의 예약 | 외부 조회 출처와 예약 실행 모드를 별도로 표시 | #4·#5: 기존 `mode=MOCK`를 실제 장소 출처 표시로 재활용하지 않음 |
| 지도 | 목적지·길 안내는 Pleos, 외부 adapter는 음식점 데이터 | #1·#5: 가용성/권한 확인, 목적지 변경 시 재조회. 카카오 지도 SDK 도입은 이 제안의 범위 밖 |
| 저장 구조 | 기존 MOCK 검색·예약과 제안 ERD를 그대로 구분 | #4: 허용 데이터·조회 계약 확정 후 별도 migration 검토 |

## 외부 미리보기 요청의 처리 순서

1. 서버가 입력 좌표·반경·상한과 지원 범위, 사용자 접근 권한을 확인합니다. 사용자 인증은 현재 미구현이므로 공용 배포 전에 별도 구현합니다.
2. 동일 화면의 진행 중 요청과 연속 조회를 제한합니다. 대기 중 재전송은 새 외부 호출로 만들지 않고 진행 상태를 반환하거나 합류시키는 방식을 #4가 결정합니다. 장소 응답을 남기는 기존 `Store.command()`를 그대로 사용하지 않습니다.
3. DB mutex와 트랜잭션 밖에서 장소 adapter를 한 번 호출합니다. 자동 반경 확대·페이지 추가·실패 재시도는 하지 않습니다.
4. 결과 수신 시 요청 세대와 현재 목적지를 대조합니다. 목적지가 바뀌었거나 화면 요청이 취소됐다면 이전 응답을 새 목적지 결과로 표시하지 않습니다. 이미 보낸 호출의 쿼터가 취소로 복구된다고 가정하지 않습니다.
5. 정상 0건·부분 불량·전체 실패를 구분해 응답합니다. 실시간 비교에 필요한 메모리 보유·수명과 브라우저/프록시 캐시 정책은 사업자 답변을 반영해 확정합니다.
6. 사용자가 예약을 누르더라도 미리보기 식별자로 기존 예약 API에 바로 진입하지 않습니다. 데이터 사용 권한, 문의 facts, 사용자 승인과 중복 예약 검증을 충족한 별도 경계가 필요합니다.

진행 상태에 필요한 식별자·좌표도 자동으로 저장 가능한 데이터라고 가정하지 않습니다. claim 복구와 중복 제한의 저장 필드, 프로세스 종료 후 재시도 정책은 #4가 보관 범위와 함께 설계합니다. 현재 idempotency snapshot 의미는 변경하지 않습니다.

## 화면에 전달할 의미

아래 이름은 의미 설명용이며 새 공개 필드나 enum을 확정한 것이 아닙니다.

| 구분할 정보 | 의미 / 표시 제안 |
| --- | --- |
| 장소 출처 | 가상 데이터 / Kakao 실시간 검색 / 별도 허가 데이터. 서로 같은 출처로 표시하지 않음 |
| 예약 실행 | 모의 실행 / 실제 문의 전 / 결과 미확인 / 명시적 수락 확인. 실제 장소 조회 성공이 실제 예약 성공은 아님 |
| 조회 상태 | 준비·조회 중·결과 있음·정상 0건·실패·취소·지원 범위 밖 |
| 장소 기본 정보 | 상호·분류·주소·출처. 전화번호는 필드가 존재해도 발신 허가가 아님 |
| 미확인 조건 | 주차·아이 동반·도착 시점 대기·예약 가능은 검색만으로 확인할 수 없음. `missing` 유지 |
| 시각 | 장소 조회 시각과 매장 문의 관측/적용/만료 시각을 분리. 검색 거리로 차량 ETA를 만들지 않음 |

표시 예: `장소 정보: Kakao 실시간 검색` / `예약: 모의 실행` / `주차·아이 동반: 확인 필요`. 정책 확인 전 시연은 `장소 정보: 가상 데이터`를 사용합니다. 현재 Android probe에는 이 화면이 없습니다.

## 오류와 재조회

| 내부 결과 | 사용자에게 전달할 상태 | 자동 처리 |
| --- | --- | --- |
| 성공 0곳 | 이 범위에서 검색 결과 없음 | 가상 식당 보충·반경 확대 없음 |
| 일부 불량 + 유효 후보 있음 | 유효 후보만 표시, 품질 정보는 안전한 요약으로 전달 | 누락 사실 생성 없음 |
| AUTHENTICATION / FORBIDDEN | 장소 검색 설정 확인 필요 | 키·사업자 원문 노출, 반복 호출 없음 |
| RATE_LIMITED | 현재 조회 제한, 잠시 후 수동 재조회 | 화면 polling·서버 자동 재시도 없음 |
| TIMEOUT / UPSTREAM_UNAVAILABLE | 검색을 완료하지 못함 | 정상 0건으로 변환하지 않음 |
| INVALID_RESPONSE | 장소 검색 응답 처리 실패 | 기존 성공 결과를 새 결과처럼 재표시하지 않음 |
| CANCELLED / 목적지 변경 | 취소 / 새 목적지로 다시 조회 필요 | 이전 요청의 늦은 응답 폐기 |

공개 HTTP 상태·오류 코드는 #4가 확정한 뒤 OpenAPI·예제·호출자·테스트를 같은 PR에서 변경합니다. 현재 내부 실패 enum을 그대로 공개 API에 노출하지 않습니다. 중복 요청, rate limit, 명시적 사용자 재조회는 서로 다른 조건으로 정의합니다.

## 채택 전에 검증할 시나리오

| 담당 | 합격 조건 |
| --- | --- |
| #2·#4 | 외부 요청 중 DB mutex가 점유되지 않음. 동시 같은 요청이 중복 외부 호출을 만들지 않음 |
| #4 | 프로세스 종료·claim 만료·클라이언트 재전송 시 호출 상한과 복구 상태가 명확함 |
| #2·#4 | HTTP 내부 재전송·앱 재시도·사용자 재조회를 합산해 실제 시범 호출 상한을 검증 |
| #4 | 저장소·명령 snapshot·HTTP/애플리케이션 로그·캐시에 허가되지 않은 장소 데이터가 남지 않음 |
| #4·#5 | 정상 0곳·1곳·부분 불량·timeout·429·취소·목적지 변경의 표시가 구분됨 |
| #3·#5 | 외부 장소 정보에 MOCK facts가 붙지 않고, 미확인 조건·승인·실제/모의 실행이 명확함 |

위 표는 후속 인수 조건이며 실행 완료 기록이 아닙니다. 현재 완료한 것은 독립 HTTP 경계의 loopback 테스트입니다. #3·#4·#5 담당자의 동의나 사업자 허가를 이 문서 작성으로 대신하지 않습니다.
