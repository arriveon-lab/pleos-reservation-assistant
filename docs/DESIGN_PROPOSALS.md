# 제품 방향과 미확정 설계 제안

기록일: 2026-11-07 KST. 아래는 대화에서 검토한 **팀 합의 전 제안**입니다. 코드·OpenAPI·DB 스키마·기존 기능 이슈의 완료 조건을 변경한 결정 기록이 아닙니다. 현행 동작은 [기능 명세](FUNCTIONAL_SPEC.md)와 [STATUS](STATUS.md)를 따릅니다.

## 1. 다중 방문 예약

현재 구현과 11개 테이블 제안은 **같은 여정의 PENDING/CONFIRMED/UNKNOWN 예약을 합쳐 최대 1개**로 제한합니다. 사용자 전체에 예약을 1개만 허용하는 정책과는 다릅니다. 현재 인증·사용자별 여정 격리는 미구현입니다.

식당과 카페 등 같은 여정의 여러 방문을 예약하려면 `trips → trip_stops → reservations` 구조를 검토합니다. 여정에 여러 방문을 두고, 활성 예약 중복 제한을 방문 일정 단위로 옮기는 안입니다. `trip_stops`는 현행 API·DB 및 11개 테이블 ERD에 없습니다.

채택 전에 #1·#4·#5가 방문 일정 식별자, 여정/목적지 변경, 일정 간 시간 충돌, 미해결 UNKNOWN, 승인 범위와 복구 조회를 합의해야 합니다. 여러 식당의 대안 예약을 동시에 확정하는 정책은 식당→카페처럼 서로 다른 방문 예약과 별도로 검토합니다. 현재 제한을 새 tripId 발급으로 우회하는 구현은 허용하지 않습니다.

## 2. 피클과 비교한 제품 방향

2026-11-06 확인한 [피클 공식 앱 소개](https://apps.apple.com/kr/app/id6795790129)는 전화 대행, 식당 등 예약, 음성 요청, 사용자 승인, 통화 진행 확인과 결과 요약, 위치·일정 활용을 안내합니다. 따라서 전화 예약·음성·승인 자체를 고유 기능으로 주장하지 않습니다. 직접 앱을 사용한 성능 비교는 하지 않았습니다.

검토한 자료에서는 Pleos 내비 목적지·ETA 직접 연동, ETA 지속 관측에 따른 예약 관리, 차량 주행 제한 대응을 확인하지 못했습니다. 공개 설명에서 미확인인 것이 기능 부재의 증거는 아닙니다. 다른 제품이 해당 기능을 구현할 수 없다는 주장도 하지 않습니다.

제안하는 제품 설명은 다음과 같습니다.

> 아이와 이동하는 운전자를 위해 도착 시각·주차·대기를 함께 고려해 식당을 예약하고, 교통 지연에 맞춰 예약을 관리하는 Pleos 비서.

아이 동반 운전자는 우선 검증할 타깃 후보입니다. 동승자는 사용자 입력으로 확인하며 차량 센서로 아동이나 가족 관계를 자동 판별한다고 가정하지 않습니다. 타깃 확정과 수요·우위는 사용자 검증이 필요합니다.

## 3. 차별화 기능 후보와 구현 경계

| 제안 | 제품에서 확인할 가치 | 현재 상태·필요한 근거 |
| --- | --- | --- |
| 도착 시각에 맞는 후보 | 현재 빈자리와 도착 시점 이용 가능성을 구분 | NOW/ARRIVAL·유효기간 평가는 MOCK 구현, 실제 장소·ETA·통화 미검증 |
| 주차·도보·대기를 포함한 비교 | 차량 이동 시간 이후 실제 입장까지 설명 | 신규 제안. 현재 API에 주차 소요/도보 소요 필드나 실측 연동 없음 |
| 지연 감지와 예약 변경 제안 | 사용자가 ETA를 다시 입력하고 매장에 연락하는 수고 감소 | 현재 지속 감지·자동 제안 미구현. 변경 API는 명시적 수동 MOCK 명령 |
| 주행 상황에 맞는 안내 | 목적지·시각 재입력과 허용되지 않는 화면 조작 감소 | 제품 UI·주행 제한·음성 통합 미구현, 기기 검증 필요 |

주차·도보·도착 대기는 출처, 적용 시각, 확인값/추정값/미확인을 구분해야 합니다. 확보하지 못한 값을 0분으로 채우거나 현재 대기를 도착 대기로 바꾸지 않습니다. 문의 결과도 미래의 빈자리나 입장 시각을 보장하지 않습니다.

Pleos의 [API 가용성](https://document.pleos.ai/docs/pleos-only/vehicle-app-planning-guide/api-compatibility-availability)은 NaviHelper를 내비 탑재 차량에서 호환으로 안내합니다. 앱의 실제 권한·콜백·ETA 시간 기준은 별도로 검증합니다. [공식 심사 기준](https://appdevchallenge.auto-hmg.io/guide/judging-awards)의 차량특화성과 SDK 활용을 보여줄 근거로, 목적지/시각 입력 횟수·화면 조작 횟수·지연 발견부터 변경 요청까지의 시간을 비교하는 검증안을 제안합니다. 측정값이나 개선율은 아직 없습니다.

## 4. 범위 변경 제안

기존 PLAN에서는 지속 ETA 지연 감지·자동 변경을 후속으로 두었습니다. 차별화를 강화하려면 **지연 감지와 변경 제안을 MVP로 승격**하는 안을 검토할 수 있습니다. 승인 범위 내 자동 발신/변경, 카페 등 다중 방문, 개인화는 이후 확장 후보로 둡니다. 아직 기존 우선순위를 변경하지 않았습니다.

1. #1이 ETA 시간 기준·갱신·목적지 변경·서비스 단절 증거를 확보합니다.
2. #4가 지연 지속 조건·관측 공백·중복 제안·변경 간격·승인/비용 정책을 정의합니다. 기존 PLAN의 임계값은 실험 초기값이며 확정값이 아닙니다.
3. #5가 정차/주행 제한에 맞는 안내와 승인·거절·미확인 결과를 설계합니다.
4. #2·#3이 도착 시점에 확인 가능한 정보와 문의/변경 결과 계약을 정합니다.
5. 범위 채택 시 실제 하위 이슈를 만들고 PLAN·기능 명세·OpenAPI·ERD·테스트를 함께 변경합니다. 이 문서에서 가상 이슈 번호를 부여하지 않습니다.
