# ArriveOn 최종 앱 화면 설계안 (#56 / #39)

2026-11-12 KST. **설계 산출물이며 release APK 완성·공동 인수는 아니다.** 구현된 MOCK 예약 기능과 아래 재구성안을 구분한다. 브라우저 시안은 [arriveon-final.html](prototypes/arriveon-final.html)을 열면 동작한다. 외부 요청·실제 전화가 없는 가상 데이터 전용 HTML이며 하단 검증 제어는 제품 화면에 넣지 않는다.

## 목표와 근거

기존 긴 진단 화면에서 목적지·조건·후보·승인·결과를 단계별로 분리한다. 한 화면에는 다음 행동 하나를 강조하고, 문의/빈자리/예약 확정을 혼동하지 않는다. 실제 추천은 3개 고정이 아니며 서버가 반환한 후보 개수만 표시한다. 음식 다중선택·반려견 등 미합의 확장을 다시 추가하지 않는다.

공식 근거(2026-11-12 열람):
- [Pleos UI 원칙](https://document.pleos.ai/docs/connect/guide/docs-design/Introduction/intro): 짧은 정보, 대비 4.5:1 이상, 일관된 용어, 지연 중 상태 안내.
- [타이포그래피](https://document.pleos.ai/en/docs/connect/guide/docs-design/foundations/typography): 정보 계층과 보조 정보 구분.
- [레이아웃](https://document.pleos.ai/en/docs/connect/guide/docs-design/getting-started/layout): 앱 창과 차량 시스템 영역 분리, 분할창 대응.
- [주행 안전](https://document.pleos.ai/docs/pleos-only/vehicle-app-planning-guide/driver-distraction-guideline): CarUxRestrictions 기반 제한, 큰 터치 영역, 텍스트 입력 최소화.

프로젝트 선택값: 주요 버튼 최소72dp, 본문22–24sp, 제목32–38sp, 카드 간격24dp. 이 수치는 Pleos가 동일 숫자를 강제한다는 뜻이 아니다. HTML의 px 표현은 구조 검토용이며 Android dp/sp·실제 물리 가독성은 이식 후 확인한다. 실차 주행 허용 판정은 별도다.

## 화면과 문구

| 화면 | 우선 표시 | 주요 행동 / API |
| --- | --- | --- |
| 조건 확인 | 목적지 출처·이름, 성인/아이, 필수 조건 | `식당 찾기` → destination-recommendations POST |
| 후보 비교 | 실제 반환 N개, 상호/주소, 확인·미확인 조건 | `이 식당 선택`은 로컬 선택만; 아직 예약 POST 없음 |
| 예약 승인 | 선택 지점, 인원, 예약 시각(KST), 필수 조건, 예약자, 추가 비용 | `이 내용으로 모의 예약 승인` → phone-reservations POST, 새 승인에 새 키 |
| 진행 중 | `모의 매장 답변을 기다리고 있어요` | 중복 승인 차단; 서버 응답 전 확정 표시 금지 |
| 결과 | 확정/거절/미확인, 식당·인원·확정 시간 | `예약 결과 다시 확인` → 같은 taskId GET; 대화 보기 |
| 대화 상세 | 서버 conversation 순서와 speaker/message | 비서/가상 매장 구분, 수동 스크롤, 결과로 돌아가기 |

현재 MOCK은 내일19시·가상 예약자·0원이며 승인 화면에 이를 명시한다. 실제 ETA에서 만든 시간처럼 표시하지 않는다. 실제 서비스용 시각 입력/예약자 정보는 백엔드 계약·개인정보 정책과 함께 별도 확정한다.

## 상태 규칙

- 상단 MOCK 표시는 항상 유지한다. 모의 매장 대화를 실제 통화 내역으로 부르지 않는다.
- 실제 내비 목적지는 SDK 수신/현재 경로 확정 상태를 구분한다. 미검증 ETA는 `미연결`로 표시하며 추정 숫자를 넣지 않는다. 고정 목적지 데모는 명시 확인으로 구분한다.
- CONFIRMED는 검증된 status와 confirmedTime을 표시한다. 대화에 '확정'이라는 단어가 있어도 상태를 추론하지 않는다.
- UNKNOWN/유실/404는 원 요청과 키를 보존하고 GET 대조만 제공한다. 자동 재발신·새 승인 생성 금지. 기존 확정 결과의 조회 실패는 이전 관측임을 명확히 안내하는 후속 UX가 필요하다.
- DECLINED에 서버가 nextCandidate를 주었을 때만 다음 후보를 새로 승인한다. EMPTY/FILTERED/FAILED/EXPIRED 각각 다른 안내와 수동 행동을 유지한다.
- 주행 제한·UNKNOWN에는 입력과 승인 및 긴 대화 열기를 차단한다. 이미 열린 대화는 숨기고 요약 결과를 유지한다. 읽기 전용 GET 복구와 새 예약을 분리한다.
- 대화가 비면 `서버에서 받은 대화 내역이 없습니다`라고 표시한다. 자동 생성/보충/타이핑 애니메이션을 넣지 않는다.
- 목적지 변경·조건 변경·뒤로 가기 시 기존 후보를 무효화하며, 진행 중 예약은 별도 원 요청으로 보존한다.

## 구현된 것과 다음 적용

이번 APK: 서버 대화 내역 펼침/접기, 화자 표시, 확정 시간 사용, 승인창 글자·버튼 확대와 줄바꿈, MOCK 후보 안내 모순 수정. 현재 화면 전체를 HTML 구조로 바꾼 것은 아니다.

시안: 입력→비교→승인→진행→결과→대화, 주야간, UNKNOWN, 차량 제한 예시. 1440px 가로 비교와840px 좁은 결과 화면/가로 넘침 없음, 버튼 흐름을 브라우저에서 확인했다. 네트워크/API 통합 검사와 구분한다.

다음 Android 적용: 화면 상태별 컨테이너 분리 → 카드/승인/결과 요약 배치 → 주야간·분할창/큰 글자/제한 재검증. 기존 ViewModel/인증/복구 journal·서버 계약은 재작성하지 않는다. 실제 후보→전화 예약은 백엔드 연결이 제공된 후 별도 검증한다. 배포 서명·실차·공동 인수·음성 예약은 완료 범위 밖이다.

MOCK 수동 실행: EC2 전용 APK의 추천 입력에서 `가상 서울숲으로 연습` → 목적지 확인 → 인원/조건 → 후보 검색 → 선택 → 승인 → 결과/대화 보기. 기존 예약이 남아 있으면 결과 조회가 우선하며, 새 테스트를 위해 원 기록을 초기화하지 않는다. 실제 내비 목적지는 변경하지 않는다.
