# 전화예약 에이전트 개발 계획

작성일: 2026년 11월 9일. 대상: 전화·AI, 서비스 서버, Pleos 앱 개발 담당자.

Telkit의 서비스 전용 070 번호와 LiveKit Agents를 이용해 식당 예약·문의 전화를 자동 진행한다. 식당이 같은 번호로 다시 전화하면 기존 예약을 확인하고, 변경 내용을 사용자에게 전달한다. 사용자 확인이 필요한 변경은 승인 후 식당과 다시 합의하여 반영한다.

이 문서는 구현 계획이다. 일정은 담당자 병행 작업을 가정한 예상치이며, 실제 전화 송수신과 한국어 품질을 검증한 뒤 확정한다.

문서 게시 이슈: [#41](https://github.com/arriveon-lab/pleos-reservation-assistant/issues/41).

이 계획은 팀 검토용 제안이며 현재 API·DB·enum을 변경하지 않는다. 현행 계약은 [API 안내](../api/README.md)와 [OpenAPI](../api/openapi.json), 실행 증거는 [STATUS](STATUS.md)를 따른다. 예시 이름은 가상 정보다.

전화 연동은 [#3](https://github.com/arriveon-lab/pleos-reservation-assistant/issues/3), 승인 증빙·영속 작업·UNKNOWN 복구는 [#4](https://github.com/arriveon-lab/pleos-reservation-assistant/issues/4), 앱 연결은 [#26](https://github.com/arriveon-lab/pleos-reservation-assistant/issues/26)과 조율한다. 이 문서의 P01~P11은 작업 분류이며 아직 발급된 GitHub 이슈 번호나 담당자 확정을 뜻하지 않는다. 문서 게시 후 범위·담당·일정을 합의하여 필요한 후속 이슈를 만든다.

실제 전화·번호 구매·유료 API 실행은 [협업 규칙](../CONTRIBUTING.md)에 따라 대상·목적·예상 비용·상한이 포함된 실행 승인을 받은 범위에서 진행한다. 이 계획의 게시 자체는 실제 실행 승인이 아니다. 장소 공급자 데이터의 보관·전화 전달 조건은 [#11](https://github.com/arriveon-lab/pleos-reservation-assistant/issues/11)과 [연동 근거](INTEGRATIONS.md)를 함께 확인한다.

## 1 목표와 개발 범위

최종 인수 시나리오는 다음과 같다.

> Pleos에서 4명 예약을 요청한다. AI가 식당에 전화해 예약을 확정한다. 식당이 070 번호로 다시 전화해 시간 변경을 요청한다. 사용자가 앱에서 승인하면 AI가 식당에 재확인하고 변경된 예약을 저장한다.

| 구분 | 개발 범위 |
| --- | --- |
| 필수 | 한국어 실시간 대화, 문의·예약 발신, 예약 결과 구조화, 회신 전화 수신 |
| 필수 | 예약 식별, 변경 요청 저장, 사용자 승인, 식당 재확인, 결과 알림 |
| 필수 | 사용자 프로필·여정별 동승자 조건 분리, 예약 당시 조건 보존, 저장 동의·수정·삭제 |
| 필수 | 중복 발신 방지, 결과 미확인 복구, 통화 제한, 오류 추적 |
| 연동 | 기존 서버의 인증·예약·알림 기능, Pleos의 요청·진행·결과·변경 승인 화면 |
| 후속 | 여러 식당 병렬 문의, 복잡한 예약 취소 협상, 자동 결제·예약금 지급, 다국어 |
| 별도 검토 | 차량 블루투스 통화 음성 추출, 여러 서비스 번호 운영, 원본 통화 녹음 |

MVP는 한 예약 요청에 한 식당을 연결한다. 식당 전화번호는 서버에서 검증한 요청 데이터로 전달하며, AI가 대화 중 임의의 번호로 새 전화를 걸도록 허용하지 않는다.

## 2 구성과 책임

```text
Pleos 앱 ← 요청·승인·상태·결과 → 서비스 서버 ↔ 예약 DB
                                      ↕ 작업·통화 결과
                                Python 통화 에이전트
                                 ↕ STT·LLM·TTS
                                LiveKit 음성 세션
                                      ↕
                               Telkit SIP 연결
                                      ↕
                                  식당 전화
```

| 구성 요소 | 책임 |
| --- | --- |
| Pleos 앱 | 이번 동승자 조건과 식당에 전달할 내용을 확인한다. 재사용 저장 선택과 예약·변경 승인을 구분하고 서버의 최신 결과를 표시한다. |
| 서비스 서버 | 프로필·여정·예약의 소유권, 조건 버전, 승인 범위, 최소 정보 전달, 작업 발행, 상태 전이, 알림과 복구를 관리한다. |
| 예약 DB | 선택 저장한 프로필, 여정별 동승자 조건, 예약 당시 조건과 확정 조건, 승인 기록, 통화·변경 이력을 분리 보관한다. |
| Python 에이전트 | 음성 대화를 진행하고, 확인된 사실을 서버 함수로 제출한다. |
| LiveKit | 음성 세션, 전화 참가자 연결, 에이전트 배정과 실시간 이벤트를 제공한다. |
| Telkit | 070 번호와 국내 전화망을 연결한다. |
| STT·LLM·TTS | 식당 발화를 텍스트로 바꾸고, 답변을 판단하고, 음성으로 재생한다. |

예약 상태의 최종 기준은 서버와 DB다. 에이전트의 대화 메모리는 통화별로 생성하고, 다음 통화에서는 DB에 저장된 예약 정보와 요약을 불러온다. 예약마다 에이전트를 새로 개발하거나 모델을 학습하지 않는다.

Telkit의 공식 LiveKit 가이드는 수신·발신 연결을 모두 안내한다. Telkit에서 음성을 실시간 텍스트로 변환해 주는 것으로 설계하지 않는다. [Telkit LiveKit 연동](https://telkit.io/docs/connect/livekit.md)

## 3 개발 전에 고정할 계약

| 항목 | 초기 설계 |
| --- | --- |
| 통화 목적 | INQUIRY, BOOKING, CALLBACK, CHANGE_CONFIRMATION, VERIFY_EXISTING |
| 예약 입력 | 식당 ID·번호, 날짜·시간, 인원, 예약자 이름, 요청 사항 |
| 동승자 조건 | 이번 여정의 총인원, 유아의자 수, 반려동물 동반, 접근성·식사 조건과 필수 여부, 사용자 확인 시각·버전 |
| 조건 재사용 | 저장한 프로필은 입력 초안으로 제시하고 이번 여정에 적용할 내용을 사용자가 확인 |
| 정보 저장 선택 | 이번 예약 처리에 필요한 저장, 다음 여정 재사용 저장, 예약·변경 승인, 학습 동의를 각각 구분 |
| 사용자 승인 | 요청 조건의 버전, 허용 시간 범위, 추가 비용 수락 범위, 승인 시각 |
| 시간 표현 | 서버 저장은 시간대가 명확한 값, 식당과 사용자에게는 한국 시간으로 안내 |
| 전화번호 | 서버에서 정규화하고, LiveKit 연결 시 E.164 형식으로 전달 |
| 초기 통화 운영 | 발신 동시성 1, 통화 최대 5분, 무응답·인식 실패 시 제한된 재질문 |
| 재발신 | 연결 실패가 명확한 경우에만 정책에 따라 최대 1회. 결과가 불명확하면 확인 절차로 전환 |
| 배포 | 수신 가능한 에이전트를 상시 운영하고, 서버·에이전트 상태를 감시 |

5분·재시도 횟수 등은 제품의 초기 제안값이며 공급자의 고정 정책이 아니다. PoC에서 대화 길이와 실패 원인을 측정해 조정한다. 새 발신 직전에 승인 유효성, 예약 버전, 취소 요청, 통화 한도를 다시 확인한다.

STT·LLM·TTS는 한국어를 지원하는 조합을 소수 선정해 같은 대본으로 비교한다. 이름·날짜·인원 인식, 부정 표현 이해, 첫 음성 응답까지의 시간, 전화 음질, 통화당 비용으로 결정한다. 채택한 SDK 버전과 모델 설정을 기록한다.

## 4 주요 통화 흐름

**예약 발신**

1. 사용자가 이번 여정의 동승자 조건, 식당에 전달할 내용, 식당·예약 조건·허용 변경 범위를 확인한다.
2. 서버가 확인된 조건의 사본(snapshot)과 승인 기록, 발신 작업을 저장한다. 재사용 프로필 저장은 별도 선택에 따라서만 수행한다.
3. 작업 실행기가 중복 실행 여부와 승인된 조건 버전을 검증한다. 승인 후 여정 조건이 바뀌었다면 새 조건으로 재확인하며, 최신 프로필을 조용히 덮어쓰지 않는다.
4. 에이전트에 예약 ID와 통화 목적을 전달하고 음성 세션을 준비한다.
5. LiveKit의 `CreateSIPParticipant`로 식당에 연결한다.
6. 상대가 응답하면 AI 비서임을 소개하고 승인된 범위에서 문의·예약한다.
7. 식당의 수락과 최종 조건을 재확인하고 서버에 결과를 제출한다.
8. 서버가 결과를 저장하면 에이전트가 마무리하고, 앱에 결과를 전달한다.

발신은 Telkit REST API로 전화를 거는 구조가 아니라 LiveKit의 SIP 참가자 생성으로 구현한다. [LiveKit 발신](https://docs.livekit.io/telephony/making-calls/outbound-calls/)

**식당 회신 수신**

1. 식당이 서비스의 070 번호로 전화한다.
2. Telkit이 LiveKit으로 연결하고, 수신 규칙이 통화별 세션에 에이전트를 배정한다.
3. 에이전트가 발신번호로 예약 후보를 조회한다.
4. 상대에게 예약자 이름·날짜·시간을 물어 예약을 특정한다.
5. 안내 사항 또는 변경 요청을 구조화해 서버에 저장한다.
6. 사용자 확인이 필요하면 확인 후 다시 연락하겠다고 안내하고 통화를 끝낸다.

발신번호만으로 상대의 권한이나 예약을 확정하지 않는다. 다른 번호·발신번호 비공개·여러 후보·미일치 상황은 별도 처리하고, 연결되지 않은 문의로 보관할 수 있어야 한다. 다른 사용자의 예약 목록을 상대에게 읽어주지 않는다.

**변경 승인과 재확인**

1. 기존 확정 내용과 변경 제안을 별도로 저장한다.
2. 미리 승인된 범위이면 서버 검증과 식당 확인을 거쳐 반영한다.
3. 승인 범위 밖이면 사용자에게 기존 조건과 제안 조건을 비교해 보여준다.
4. 사용자 승인 후에도 식당의 변경 가능 여부를 다시 확인한다.
5. 식당까지 합의한 경우에만 새 조건을 확정한다.
6. 사용자가 거절하거나 응답하지 않으면 변경 완료로 표시하지 않는다.

식당이 기존 예약을 이행할 수 없다고 통보하면 기존 조건은 이력으로 보존하되, 현재 상태를 정상 확정으로 계속 표시하지 않는다. 이행 불가 통보와 후속 대응 필요 상태를 저장해 알린다. 거절 후 기존 예약이 유지되는지도 필요한 경우 식당에 확인한다.

## 5 대화 규칙과 에이전트 함수

에이전트는 짧은 문장으로 한 가지씩 확인한다. 날짜는 월·일, 시간은 오전·오후 또는 저녁 등으로 풀어 말하고, 이름·인원·시간을 마지막에 다시 확인한다. “잠시만요”, “확인해볼게요”, “그 시간은 안 돼요”를 예약 수락으로 처리하지 않는다.

발화 종료 감지와 상대의 끼어들기를 처리한다. 식당이 말을 시작하면 TTS 재생을 중단하고 새 발화를 듣는다. 잘못 들은 숫자는 추정해서 저장하지 않고 다시 묻는다. 자동응답·안내멘트·음성사서함은 예약 수락으로 해석하지 않는다. 복잡한 ARS는 초기 버전에서 확인 필요로 종료하고, 필요성이 확인되면 단순 번호 입력을 추가한다.

| 내부 함수 제안 | 입력·동작 | 서버 검증 |
| --- | --- | --- |
| `get_booking_context` | 예약 ID로 승인된 조건 사본·필수 동승자 조건·승인·관련 이력 조회 | 작업에 허용된 예약인지 확인하고 식당에 전달할 최소 필드만 반환 |
| `find_callback_candidates` | 발신번호·상대가 제시한 조건으로 후보 탐색 | 최소 정보만 반환하고 복수 후보를 구분 |
| `submit_call_outcome` | 결과, 합의 조건, 동승자 필수 조건별 확인 결과, 근거 발화, 통화 ID 제출 | 허용 범위·승인된 조건 버전·중복·필수 조건 충족 검증 |
| `create_change_request` | 변경 내용과 사유 저장 | 원 예약 보존, 변경 버전과 만료 관리 |
| `mark_needs_review` | 식별 불가·통화 단절·모호한 결과 기록 | 자동 확정·중복 신규 예약 방지 |
| `finish_call` | 마무리 음성 완료 후 세션 종료 | 중요 결과 저장 여부와 종료 사유 확인 |

이 함수들은 구현할 내부 계약이며 Telkit의 제공 API가 아니다. 대화 내용으로 시스템 지침, 예약 소유권, 비용 상한, 서버 검증 규칙을 변경하지 못하도록 한다.

에이전트에는 전체 프로필이나 동승자 명단을 조회·수정하는 도구를 제공하지 않는다. 통화 중 상대가 조건 수정을 요구하면 이번 예약의 변경 제안으로 기록하고, 다음 여정에 쓸 프로필을 자동으로 고치지 않는다. 유아의자·반려동물·접근성·식사 관련 필수 조건은 취향보다 우선하며, 미확인이나 충족 불가를 가능으로 바꾸지 않는다. 필수 조건의 근거가 부족하면 추가 질문 또는 사용자 확인으로 전환하고 예약 확정 처리를 보류한다.

예약 완료 후에는 다음과 같이 안내한다.

> “11월 15일 저녁 7시, 4명, 김예약 이름으로 예약 확인했습니다. 변경 사항이 있으면 지금 전화드린 번호로 연락 부탁드립니다. AI 예약 비서가 받아 예약자에게 전달하겠습니다.”

회신 안내는 수신·변경 저장·사용자 알림까지 정상 동작하는 배포에서 사용한다. 사용자에게 알림을 저장한 것과 사용자가 실제 확인한 것을 구분한다.

## 6 상태와 저장 모델

| 대상 | 제안 상태 |
| --- | --- |
| 통화 | QUEUED → DIALING → ACTIVE → ENDED, 또는 FAILED |
| 예약 | AWAITING_APPROVAL → PROCESSING → CONFIRMED / DECLINED / UNKNOWN |
| 예약 예외 | 식당 이행 불가 통보 시 NEEDS_RESOLUTION |
| 변경 | RECEIVED → AWAITING_USER → RECONFIRMING → APPLIED / REJECTED / EXPIRED / UNKNOWN |

통화 종료와 예약 확정은 독립적이다. 변경 중에는 원 예약의 확정 조건과 변경 제안을 함께 유지한다. 예약 취소 확정은 명확한 취소 요청과 식당 확인이 있는 후속 흐름으로 추가한다.

| 저장 대상 | 최소 필드 |
| --- | --- |
| 사용자 프로필 | 소유 주체 ID, 예약 표시 이름, 선택 저장한 선호·동승 조건 템플릿, 저장 목적·범위, version, 수정·만료 시각 |
| 여정별 동승자 조건 | trip_id, 소유 주체, 총인원, 유아의자 수, 반려동물 동반, 접근성·식사 조건, 필수 여부, 확인 시각, version |
| 예약 당시 조건 사본 | snapshot_id, booking_id, 원 여정·조건 버전, 승인된 인원·요구 조건·전달 필드, 생성 시각 |
| 예약 | booking_id, 소유 사용자, 식당, snapshot_id, 요청 조건, 확정 조건, 상태, version |
| 승인 | booking_id, snapshot_id·조건 버전, 허용 범위, 승인자·시각 |
| 정보 저장 선택 | 소유 주체, 목적, 필드 범위, 선택 여부, 정책 버전, 선택·철회 시각 |
| 통화 시도 | call_attempt_id, booking_id, 목적·방향, LiveKit room·참가자 식별자, 공급자 통화 ID, 결과·시각 |
| 대화 근거 | 통화 ID, 화자, 확정 발화, 시각, 결과 판단에 사용한 구간 |
| 변경 요청 | change_id, booking_id, 이전 버전, 제안, 승인·식당 확인 결과, 만료 시각 |
| 작업·이벤트 | event_id, 중복 방지 키, 작업 상태, 재시도 횟수, 실행 기한 |
| 사용자 알림 | 예약·변경 ID, 내용, 생성·전달·열람 시각 |

공급자 통화 ID는 연동 과정에서 수집 가능 여부와 전달 경로를 확인한다. 확보되지 않으면 방향·번호·시각을 이용한 기록 대조를 보조적으로 사용하되, 애매한 기록을 자동으로 연결하지 않는다.

### 사용자 프로필과 이번 동승자 조건

사용자는 기존 인증 주체로 식별한다. 에이전트가 개인정보를 계속 기억하는 방식에 의존하지 않고, 서버가 이번 예약에 필요한 정보만 골라 전달한다. 동승자 정보는 사람별 신원 목록보다 예약에 필요한 조건으로 관리하며, 이름·생년월일·관계·정확한 나이는 기본 수집 항목에서 제외한다.

| 조건 | 제안 필드 | 확인 규칙 |
| --- | --- | --- |
| 총인원 | `partySize` | 이번 예약에 포함되는 전체 인원으로 사용자가 확인 |
| 유아의자 | `highChairCount` | 필요한 개수. 인원과 함께 확인하고 임의 추정하지 않음 |
| 반려동물 | `petAccompanied` | 동반·비동반·미확인을 구분하고, 미입력을 비동반으로 처리하지 않음 |
| 접근성 | `accessibilityRequirements` | 계단 없는 입장 등 예약에 필요한 요구 사항만 기록 |
| 식사 조건 | `dietaryRequirements` | 사용자가 직접 입력·확인한 조건만 사용하며 건강 상태를 추론하지 않음 |
| 중요도·확인 상태 | `requirementLevel`, `verificationStatus` | 필수·선호와 확인됨·미확인·충족 불가를 구분 |

필드명은 구현 계약 초안이다. 저장한 템플릿을 불러와도 매 여정마다 현재 동승자와 총인원을 확인한다. 오래된 조건을 이번 여정의 사실로 자동 적용하지 않는다. 예를 들어 “총 4명, 유아의자 1개, 계단 없이 입장 필요”만으로 식당에 필요한 문의를 진행할 수 있다.

### 예약 당시 조건 보존

발신 승인 시 사용자에게 보여준 인원·필수 조건·식당 전달 범위를 버전이 있는 사본으로 저장하고 승인 기록과 연결한다. 프로필·여정 조건 수정은 기존 예약 사본이나 확정 내용을 자동으로 변경하지 않는다. 예약에 반영하려면 별도의 변경 요청과 필요한 사용자 승인·식당 확인을 거친다.

회신 전화에서도 해당 예약의 사본과 합의된 변경 이력을 기준으로 응대한다. 조회 시점의 최신 프로필로 과거 예약을 재구성하지 않는다. 저장된 사본의 변경 방지는 업무 변경에 대한 규칙이며, 명시적인 정보 삭제 요청이나 보관 기한에 따른 개인정보 삭제·마스킹을 막는 규칙은 아니다.

## 7 서버와 앱 연동 계약

아래 경로는 새 기능의 계약 초안이다. 기존 서비스의 API 경로와 인증·응답 규칙을 확인하여 맞춘다. 표의 식별자·상태는 개념 제안이며 현행 필드·enum과 대조한다. 공개 API의 JSON 필드는 저장소 규칙에 따라 camelCase를 사용한다. 계약 변경은 OpenAPI·예제·호출자·테스트와 함께 별도 구현 PR에서 반영한다.

| 기능 | API 예시 | 핵심 동작 |
| --- | --- | --- |
| 프로필 관리 | `GET/PATCH /me/profile` | 소유 주체의 선택 저장 정보 조회·수정, 조건 버전 검사 |
| 재사용 저장 선택 | `PUT /me/profile/storage-preferences` | 목적·필드별 저장 선택 및 철회, 예약 승인·학습 동의와 분리 |
| 저장 프로필 삭제 | `DELETE /me/profile` | 재사용 프로필 삭제, 예약 사본의 별도 보관 범위를 안내 |
| 여정 조건 확인 | `GET/PUT /trips/{tripId}/party-conditions` | 이번 동승자 조건 조회·확인·수정, 타인 여정 접근 차단 |
| 정보 삭제 요청 | `POST /me/data-deletion-requests` | 프로필·여정·예약 사본 등 삭제 범위를 지정하고 처리 상태 제공 |
| 요청 생성 | `POST /bookings` | 여정 ID·조건 버전을 연결해 요청 저장, 중복 방지 키 처리 |
| 발신 승인 | `POST /bookings/{id}/approvals` | 확인한 조건 사본과 승인 범위를 저장한 뒤 작업 생성 |
| 상태 복구 | `GET /bookings/{id}` | 예약·진행 통화·변경 요청의 최신 상태 반환 |
| 변경 결정 | `POST /bookings/{id}/changes/{changeId}/decision` | 승인·거절과 버전 검증, 재확인 작업 생성 |
| 진행 이벤트 | 인증된 SSE 또는 기존 실시간 채널 | 서버가 확인한 상태·요약 전달 |
| 내부 결과 제출 | `POST /internal/call-attempts/{id}/outcome` | 에이전트 인증·중복·상태 전이 검증 |

요청 생성·발신·결과 저장·알림은 재전송되어도 한 번만 반영하도록 한다. 예약 변경과 발신 작업 기록을 같은 DB 트랜잭션에 저장하고, 작업 실행기가 기록을 읽어 처리하는 outbox 방식을 적용한다.

진행 이벤트에는 순서를 구분할 수 있는 버전을 넣는다. 앱은 재접속 시 조회 API로 복구하고, 이벤트만으로 예약 결과를 확정하지 않는다. 앱이 종료되어도 읽지 않은 알림을 DB에 유지한다. 백그라운드 알림 수단은 Pleos 기기에서 검증한다.

앱은 “이번 동승자 조건 확인 → 식당에 전달할 내용 확인 → 예약 승인” 흐름을 제공한다. “다음에도 기억하기”는 별도 선택이며 기본은 꺼짐으로 제안한다. 재사용 저장을 선택하지 않아도 이번 예약은 진행할 수 있고, 회신·변경 처리를 위해 예약 조건이 정해진 기간 보관된다는 점을 안내한다. 프로필 수정 시 기존 예약에 자동 적용되지 않음을 표시하고, 적용하려면 해당 예약의 변경 절차로 이동한다. 저장 정보 조회·수정·삭제와 삭제 처리 상태 화면을 포함한다. 주행 중 편집·확인 동작은 기존 차량 UX 제한에 맞춘다.

## 8 전화 연결과 운영 준비

1. LiveKit 프로젝트와 기본 에이전트를 만들고 마이크 대화를 확인한다.
2. Telkit 계정의 본인인증·카드 등록과 서비스 번호 준비를 완료한다.
3. LiveKit inbound trunk에 번호·허용 접속·미디어 암호화를 설정한다.
4. 통화별 세션 생성과 에이전트 배정을 위한 dispatch rule을 만든다.
5. Telkit 번호의 수신 목적지를 LiveKit SIP URI로 연결하고 번호 형식을 맞춘다.
6. Telkit 발신 자격 정보를 서버에 보관하고 LiveKit outbound trunk를 구성한다.
7. 팀원 번호로 수신·발신·양방향 음성·표시 번호·종료 처리를 각각 확인한다.
8. 에이전트를 상시 실행 환경에 배포하고 장애·잔액·수신 가용성을 관측한다.

Telkit 발신은 TLS 연결과 G.711 PCMA/PCMU 코덱을 사용하도록 구성한다. 인증 정보·미디어 암호화·수신 IP 허용은 [공식 연동 가이드](https://telkit.io/docs/connect/livekit.md)의 현재 설정에 맞춘다. LiveKit의 수신 IP 제한은 프로젝트 활성화 조건도 확인한다.

Telkit의 동시 통화 한도는 수신·발신 합계 4통이다. 발신 동시성을 1로 시작하고, 실행 중인 모든 세션을 고려해 새 발신을 제한한다. 수신도 동시에 몰릴 수 있으므로 여유 슬롯을 남기는 것만으로 수신 성공을 보장하지 않는다. [한도와 동시 통화](https://telkit.io/docs/numbers/limits.md)

현재 Telkit `call.ended` 웹훅은 준비 중이며 통화 기록은 종료 후 약 30초 뒤 생성된다. 실시간 상태는 LiveKit·에이전트 이벤트로 관리하고, Telkit 기록은 종료 후 비용·연결 결과 대조에 사용한다. 공급자의 통화 성공 기록은 식당의 예약 수락 근거를 대신하지 않는다. [통화 결과와 웹훅](https://telkit.io/docs/operate/call-events.md)

## 9 실패와 복구

| 상황 | 처리 원칙 |
| --- | --- |
| 통화 중·무응답 | 실패 사유 저장, 정책 범위에서만 재시도 |
| 연결 요청의 응답 유실 | 현재 세션·참가자를 대조하고 즉시 중복 발신하지 않음 |
| 예약 대화 후 갑작스러운 단절 | 확정 근거와 저장 결과를 대조, 불명확하면 UNKNOWN |
| 에이전트·서버 재시작 | DB 작업과 세션 상태를 대조하고 중복 실행을 차단 |
| STT·LLM·TTS 오류 | 제한된 복구 후 확인 필요 처리, 예약 성공으로 간주하지 않음 |
| 결과 저장 실패 | 같은 통화 ID로 재제출, 복구 전 앱에 성공을 단정하지 않음 |
| 변경 승인 중 다른 변경 도착 | 예약·변경 버전 충돌을 검출하고 최신 조건 재확인 |
| 승인 후 프로필·여정 조건 수정 | 승인된 사본 유지, 새 조건으로 발신하려면 재확인·승인. 진행·확정 예약은 변경 절차 사용 |
| 저장 선택 철회·삭제 중 통화 작업 | 삭제 범위와 작업 상태 대조, 대상 정보의 새 조회·전달 차단, 필요한 작업은 확인 필요 처리 |
| 사용자 취소와 발신 경합 | 발신 직전 취소 확인, 이미 연결됐으면 진행 사실과 결과를 보존 |
| 앱 연결 단절 | 알림 저장, 앱 복귀 시 최신 상태 재조회 |
| 잔액·회선·한도 문제 | 새 작업 제한, 원인 표시, 운영 담당자에게 알림 |

UNKNOWN은 신규 예약 자동 재시도의 대상이 아니다. 기존 예약이 생성됐는지 확인하는 VERIFY_EXISTING 작업이나 운영 담당자의 확인 절차로 해결한다. 한도 관리는 DB 기반 작업 잠금과 만료·실행 중 상태 대조를 함께 사용한다.

## 10 보관과 비용 관리

서비스 키·SIP 비밀번호는 서버의 비밀값 저장소에서 관리하고 앱이나 일반 로그에 넣지 않는다. 에이전트에는 이번 통화에 필요한 최소 예약 정보만 제공한다. 예약·변경·대화 조회에 사용자 소유권을 적용한다.

정보를 기억하는 선택은 네 가지 목적을 구분한다. 재사용 프로필 저장 선택은 다음 여정의 입력 편의에만 적용한다. 이번 예약의 요청·조건 보관은 예약 수행·회신·변경 처리에 사용한다. 예약·변경 승인은 특정 조건 버전에서 실행 가능한 범위를 정한다. 학습 동의는 별도 항목이며 프로필 저장이나 예약 승인을 학습 동의로 해석하지 않는다. 이 계획에서 모델 학습 기능은 구현하지 않는다.

| 정보 종류 | 보관·수정·삭제 기준 |
| --- | --- |
| 재사용 프로필·동승 조건 템플릿 | 선택한 필드만 저장하고 조회·수정·삭제 제공. 저장 선택 철회 시 해당 재사용 정보 제거 |
| 여정별 임시 조건 | 여정 종료 후 처리 중 예약과 무관한 정보는 정리. 예약·회신에 필요한 조건은 별도 예약 사본에서 관리 |
| 예약 당시 조건·변경 이력 | 예약 처리와 정해진 사후 대응 기간에 필요한 최소 내용만 유지. 기간 종료 시 삭제·마스킹 |
| 식사·접근성 관련 정보 | 이번 예약에 필요한 요구 사항만 전달. 건강 관련 상세 내용은 기본 재사용 저장 대상에서 제외하고 별도 선택 범위를 정의 |
| 대화·진단 로그 | 동승자 상세·전화번호를 일반 로그에 복제하지 않음. 별도 보관 기한을 적용하고 삭제 작업에 포함 |

P01에서 정보 종류별 보관 기간, 만료 시각, 삭제 범위와 예약 진행 중 삭제 처리 규칙을 확정하고 P05에 자동 정리를 구현한다. 미해결 예약이라는 이유로 무기한 보관하지 않도록 기한과 후속 확인 절차를 정한다. 사용자는 재사용 프로필만 삭제하는 것과 예약 사본을 포함한 정보 삭제를 구분할 수 있어야 한다. 이미 식당에 전달된 내용은 우리 DB 삭제로 회수되는 것이 아니므로 삭제 완료 범위를 정확히 표시한다. 처리 중 예약에 필요한 정보가 삭제되면 기존 개인정보를 몰래 복원하지 않고 자동 처리를 보류해 사용자에게 필요한 확인을 안내한다.

원본 음성 녹음은 MVP 기본 기능에서 제외한다. 대화 텍스트와 근거 발화는 보관 기간·삭제 기준·접근 주체를 정한 뒤 저장하며, 앱에 제공하는 요약과 운영 진단 로그를 구분한다.

비용은 번호 요금, 전화 통신비, LiveKit, STT·LLM·TTS, 서버·DB로 나눠 관측한다. 하루 발신·통화 시간 상한을 설정하고, 긴 침묵·무한 재질문을 종료한다. 새 발신만 중단하는 기능과 모든 통화를 긴급 종료하는 기능을 구분한다.

Telkit 요금은 현재 번호 30일당 7,000원, 수신 10초당 2원, 휴대폰 발신 10초당 12원, 유선 발신 분당 15원이며 부가세 별도다. 통화마다 과금 단위로 올림 처리한다. 전체 통화당 비용은 PoC에서 AI·LiveKit 사용료까지 합산해 측정한다. [번호와 요금](https://telkit.io/docs/numbers/pricing.md)

## 11 작업 순서와 산출물

일정은 개발 착수일 D1부터 15영업일을 기준으로 한다. 전화·AI, 서버, 앱 역할이 병행하는 가정이며 실제 인원 배정은 팀에서 결정한다.

| ID | 일정 | 작업 | 담당 역할 | 선행 | 산출물·완료 기준 |
| --- | --- | --- | --- | --- | --- |
| P01 | D1~2 | 프로필·여정 조건·예약 사본·승인 계약 확정 | 서버·AI·앱 | 없음 | 필드·필수 조건·저장 선택·버전·보관/삭제·오류 계약 합의 |
| P02 | D1~2 | 계정·설정·실행 환경 준비 | 전화·AI | 없음 | 비밀값 분리, 로컬 에이전트 실행 |

D5에 실제 송수신과 한국어 대화의 진행 가능 여부를 판단한다. 실패한 계층이 전화 연결인지, 음성 처리인지, 대화 로직인지 나눠 수정한다. 전화 연결이 지연되면 가상 통화 이벤트로 서버·앱 개발을 이어가되 실제 통화 완료로 표시하지 않는다.

프로필·동승자 조건 관리는 P01·P05·P06·P08에 포함한다. 기존 구현 재사용 가능 범위와 삭제·보관 정책 확정에 따라 작업량이 늘 수 있으므로, 15영업일 예상은 P01에서 다시 산정한다.

## 12 검증과 출시 기준

| 테스트 | 기대 결과 |
| --- | --- |
| 재사용 저장 미선택 | 프로필을 만들지 않고도 이번 예약 진행, 필요한 예약 사본만 보관 |
| 저장 프로필을 다음 여정에 불러오기 | 현재 인원·조건을 확인하기 전 자동 적용·발신하지 않음 |
| 프로필·여정 조건 수정 | 기존 예약 사본·확정 인원·조건 보존, 변경은 별도 절차로 처리 |
| 승인 직전·직후 조건 버전 충돌 | 승인한 화면과 다른 조건으로 전화하지 않고 재확인 |
| 유아의자·반려동물·접근성·식사 필수 조건 | 미확인·충족 불가를 충족으로 처리하지 않고 선호보다 우선 |
| 에이전트·회신의 정보 조회 | 해당 예약에 필요한 필드만 전달, 전체 프로필·다른 여정·동승자 신원 비노출 |
| 저장 선택 철회·삭제·보관 만료 | 지정 범위 제거·마스킹, 로그·대기 작업에서도 재사용 차단 |
| 진행 중 예약 정보 삭제 | 삭제 범위·처리 결과를 표시하고 필요한 자동 처리는 보류, 정보 자동 복원 없음 |
| 학습·저장·예약 승인 구분 | 한 선택을 다른 목적의 동의나 실행 권한으로 사용하지 않음 |
| 정상 예약 수락 | 식당이 확인한 날짜·시간·인원·이름과 DB·앱이 일치 |
| 거절·모호한 답변 | 예약 불가 또는 추가 확인으로 처리 |
| 이름·숫자·날짜 정정 | 정정 내용을 다시 확인하고 최종 조건 반영 |
| 소음·침묵·끼어들기 | 제한된 재질문과 음성 중단이 자연스럽게 동작 |
| ARS·안내멘트 | 사람의 예약 수락으로 오인하지 않음 |
| 승인 범위 밖 변경 | 임의 확정 없이 사용자 확인으로 전환 |
| 식당의 기존 예약 이행 불가 | 정상 확정 상태로 방치하지 않고 대응 필요 표시 |
| 같은 식당의 복수 예약 | 정확히 식별한 예약만 처리, 타 사용자 정보 노출 없음 |
| 다른 번호·비공개 번호 회신 | 추가 확인 또는 미연결 문의로 접수 |
| 사용자 승인·거절·무응답 | 식당 재확인·보류·만료가 정책대로 동작 |
| 요청·이벤트 중복 | 작업·결과·알림이 중복 반영되지 않음 |
| 예약 수락 직후 단절 | 근거 확인 또는 UNKNOWN, 신규 예약 자동 재발신 없음 |
| 서버·에이전트 재시작 | 원장과 실제 세션을 대조하고 중복 실행 방지 |
| 앱 종료·재접속 | 최신 상태와 읽지 않은 알림 복구 |
| 동시 통화·잔액·비용 상한 | 제한을 적용하고 원인을 관측 가능 |
| 예약 권한 위반·대화 중 지침 변경 요구 | 다른 예약 접근이나 서버 규칙 변경 차단 |

검증은 서버 상태·동시성 테스트, 가상 대화 시나리오, 협의된 번호와의 실제 통화, Pleos 기기 인수 순서로 진행한다. AI의 문장 표현보다 최종 조건·상태·호출한 함수·금지된 변경 여부를 검증한다.

출시 전 인수 세트에서 잘못된 예약 확정, 중복 예약, 다른 사용자의 예약 변경은 0건이어야 한다. 정상·거절·단절·변경·회신 시나리오를 각각 반복하고, 통화 ID와 기대·실제 결과를 기록한다. 이는 해당 테스트 세트의 통과 기준이며 운영에서 오류가 없음을 보장하는 수치는 아니다.

응답 지연은 상대 발화 종료부터 AI 첫 음성까지 측정하고 p50·p95를 기록한다. 첫 PoC는 대체로 2초 안팎을 목표로 삼되, 실측으로 제품 기준을 확정한다. 통화당 총비용, 잘못 인식한 예약 필드, UNKNOWN 비율, 회신 식별 실패, 알림 전달 지연도 함께 관측한다.

최종 산출물은 에이전트 코드·실행 안내, 고정된 모델·SDK 설정, 서버 API 계약, DB 변경, SIP 설정 안내, 배포·복구 절차, 테스트 결과, 실제 시연 영상이다. 코드와 문서에 자격 증명은 포함하지 않는다.

## 13 첫 착수 작업

- [ ] 프로필·이번 동승자 조건·예약 사본·승인 범위·결과·변경 요청 계약을 확정한다.
- [ ] 재사용 저장 선택, 필드별 전달 범위, 보관 기한·삭제·만료 처리 기준을 확정한다.
- [ ] LiveKit Python 기본 에이전트를 생성하고 한국어 마이크 대화를 확인한다.
- [ ] 예약 수락·거절·시간 변경·애매한 답변 대본을 작성한다.
- [ ] 서버에 프로필·여정 조건·예약 사본·저장 선택과 예약·통화·변경·중복 방지 구조를 구현한다.
- [ ] 앱에 이번 동승자 조건 확인, 다음에도 기억하기, 프로필 수정·삭제와 예약 승인 흐름을 연결한다.
- [ ] Telkit·LiveKit 수신·발신 설정을 준비하고 팀원 번호로 각각 검증한다.
- [ ] 첫 예약 결과를 서버에 저장하고 앱에서 조회한다.

시작 템플릿과 실행·배포 흐름은 [LiveKit Voice AI quickstart](https://docs.livekit.io/agents/start/voice-ai/)를 따른다. 실시간 텍스트를 연결할 때는 [LiveKit Text and transcriptions](https://docs.livekit.io/agents/multimodality/text/)의 현재 인터페이스를 사용한다.
