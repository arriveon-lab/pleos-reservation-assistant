# REC-05 · 오래된 검색 복구와 미리보기 정리 안내

2026-11-10. #16 서버 / #26 앱 / #17 수명 정책. [화면 담당 요청](https://github.com/arriveon-lab/pleos-reservation-assistant/issues/16#issuecomment-6759209219)에 대한 서버 계약입니다. 기본 MOCK이며 검색·전화·예약·외부 조회를 실행하는 복구 API가 아닙니다.

## 오래된 검색 명령 대조

`POST /api/v1/searches/reconcile`에 **원래 검색 본문**, **원래 Idempotency-Key**, **같은 설치 주체의 Bearer 토큰**을 보냅니다. 같은 주체의 정상 refresh는 가능합니다. 원 키·시각·tripId·본문·인증 바인딩을 수정하거나 새 주체로 우회하지 않습니다. 정상 요청 형식은 [SearchRequest](../api/examples/search.json), 응답은 [완료 예제](../api/examples/search-reconciliation-completed.json)와 [종료 예제](../api/examples/search-reconciliation-rejected-closed.json)를 참고합니다. 예제 시각은 고정 설명용입니다.

| 응답 | 서버 의미 | 앱의 다음 동작 |
| --- | --- | --- |
| 200 COMPLETED + searchId | 같은 주체·키·본문의 검색이 이미 커밋됨. 분실 응답 대조 | searchId로 GET하여 현재 상태 확인. 기존 요청의 대조 결과를 journal에 원자적으로 저장한 뒤 pending을 해소. 자동 문의·예약 금지 |
| 200 REJECTED_CLOSED + INVALID_TIME | 처리 기록이 없고 ETA가 현재 이하인 원 요청을 영속 종료 | 종료 응답과 원 명령의 연결을 저장한 뒤 pending을 해소. 사용자에게 새 검색을 명시적으로 시작하도록 안내 |
| 200 REJECTED_CLOSED + STALE_NAVIGATION | 처리 기록이 없고 관측이 300초보다 오래된 원 요청을 영속 종료 | 동일. 새 입력은 최근 관측·미래 ETA와 새 키를 사용하고 같은 여정이면 tripId 유지 |
| 409 KEY_REUSED | 기존 검색 또는 종료 기록과 본문 fingerprint 불일치 | 원 요청 보존, 입력 차단 유지. 키를 바꿔 우회하지 않고 대조 필요 안내 |
| 409 REQUEST_NOT_CLOSABLE | 완료 기록은 없으나 확정된 오래된 입력이 아님 | 미해결 유지. 정상 입력·미래 ETA 24시간 초과·미래 관측·미검증 PLEOS를 임의 종료하지 않음 |
| 401 / 404 / 5xx / 통신·해석 오류 | 종료 확인 없음. 구버전 서버의404도 성공이 아님 | 원 요청 유지. 같은 주체 refresh 또는 명시적 동일 대조 재시도만 허용 |

추천 문구는 종료 확인 후 **“이전 검색 요청을 종료했습니다. 현재 조건으로 다시 검색해 주세요.”**입니다. 응답을 받았더라도 앱의 journal 저장이 실패하면 입력을 해제하지 않습니다. 원 명령을 지우는 우회 대신, 원 명령과 대조 결과를 연결하는 종료 기록을 앱의 보관 정책 안에서 보존합니다. 검색 중단을 예약 취소로 표현하지 않습니다.

서버는 기존 `commands`의 별도 `search-closure` 범위에 본문 hash·최소 대조 응답을 저장합니다. 새 migration이나 원 검색/예약/통화 payload 변경은 없습니다. 전체 명령 mutex 아래에서 기존 검색을 먼저 확인하므로 동시 검색·대조가 이중 실행/상반된 종료를 만들지 않습니다. 미처리·오래된 요청의 종료 후 원 `/searches` 재전송은409 `SEARCH_COMMAND_CLOSED`; 시계가 뒤로 돌아도 재실행되지 않습니다. 처리된 검색은 기존 snapshot 재전달을 유지하며 최신 유효성은 GET에서 확인합니다.

원래400 거절은 트랜잭션 rollback으로 저장되지 않았으므로 대조 응답은 **최초 거절의 이력을 증명하지 않습니다.** 동일 주체·키·본문의 완료 기록 유무와 현재 오래된 조건을 잠금 안에서 판정하고 이후 실행을 막는 절차입니다. 일반적인 예약·통화 명령의 종료 API가 아닙니다. 단일 로컬 MOCK 서버/같은 인증 DB가 전제이며 원 DB 소실·다른 서버 DB·만료 인증의 강제 복구나 다중 서버 원장을 해결하지 않습니다.

핵심 호환 표식1.1.0과 미리보기0.2.0-draft는 유지합니다. 새 대조 연산은 [OpenAPI](../api/openapi.json)에 명시된 추가 기능이며 기존 앱은 자동 채택하지 않습니다.

## 만료 후 PREVIEW_NOT_FOUND

미리보기는 메모리 세션입니다. 없는 ID·idle 만료·close로 제거·서버 재시작·타인 소유를 모두404 `PREVIEW_NOT_FOUND`로 처리합니다. 원인을 구분하면 소유권/존재 정보가 노출되므로 구분 응답을 추가하지 않습니다. **예약이나 통화의 취소 성공과도 관계없습니다.**

- 결과는 목적지/조건 변경·화면 이탈·만료 시 먼저 숨기고, 늦은 응답으로 복원하지 않습니다.
- 명시적 close의200은 해당 세션 종료 확인입니다. cancel의200은 generation별 응답 필드대로 판단하며, 취소되지 않았다는 결과를 취소 성공으로 바꾸지 않습니다.
- 정확한404/PREVIEW_NOT_FOUND는 **“이전 추천은 숨겼습니다. 서버에서 미리보기를 찾지 못해 정리 완료는 확인하지 못했습니다.”** 정도로 안내합니다. 이미 EXPIRED이면 만료 안내를 주 상태로 유지하고 정리 미확인을 보조로 표시합니다.
- 일반404·깨진/큰 오류 본문·네트워크 실패·503은 별도 실패입니다. 자동 재검색·반복 정리·키/주체 교체·제한 우회는 하지 않습니다.
- 사용자가 새 검색을 명시할 수 있는지는 기존 pending 명령·인증·CarUx·세션 제한 규칙대로 판단합니다. 이404만으로 다른 미해결 명령을 해제하지 않습니다.

이 안내는 앱26e80cf의 현재 보수적 처리와 일치합니다.404를 성공으로 바꾸는 앱 수정은 필요하지 않습니다. #17의 영속 원장·재시작 대조는 별도 후속입니다.

## 검증과 화면 담당 인수

서버의 정상/거절/소유자/키 충돌/동시성/rollback/경계 및 실제 토큰 HTTP 테스트, 패키징 JAR의 H2 재시작 후 종료 기록·완료 응답 보존을 검사합니다. `scripts/auth-smoke.py`가 새 API 호출자이며 `scripts/smoke-test.py --check-contract`와 Docker 검사에서 같은 계약을 대조합니다.

앱 최신26e80cf의 AuthSession/MockRepository/PreviewController를 읽기 전용 checkout에서 컴파일해4fixture·앱 HTTP52·schema HTTP48을 직접 검사합니다. **호스트 JVM의 기존 미리보기 연결 증거**이며 새 복구 버튼, Android journal/Keystore·화면·실제 기기의 새 서버 실행 증거는 아닙니다.

화면 담당은 새 서버 commit에 맞춰 명시적 “이전 검색 확인/종료” 동작을 연결하고 다음을 확인해야 합니다.

1. 기존 pending 원본·인증 보존 → 동일 대조 → 종료 기록/입력 해제의 원자적 journal 저장.
2. 응답 유실·앱 재시작은 동일 대조 응답 재전달. 저장 실패 시 차단 유지. 완료된 검색은 GET 복구.
3. 다른 본문/주체·구버전404·네트워크 실패는 해제 금지. 종료 후 사용자 새 검색은 새 키·최근 입력·같은 tripId.
4. 최종 APK SHA·서버 commit/image·Pleos 버전을 고정해 기존 설치의 원 요청 복구를 확인. 기존 journal/Keystore 삭제나 신규 주체 발급으로 대체하지 않음.

기존 기기 검증/이번 서버 검증/새 화면 인수는 구분합니다. 최종 앱 연결과 실제 원 요청 복구 전에는 #16/#26 공동 인수 완료·PR #19 병합으로 표시하지 않습니다.
